# Бақылау және кезекшілік

Бұл қалтада JUZBOOK-тың бақылау жүйесі сипатталған: қандай өлшемдер
жиналады, тақтада не көрінеді, дабыл қашан шығады және оған кім жауап
береді.

## Қысқаша

| Бөлік | Қайда |
|---|---|
| OpenTelemetry іске қосылуы | [`instrumentation.ts`](../instrumentation.ts) |
| Қолданбаның өз өлшемдері | [`lib/telemetry.ts`](../lib/telemetry.ts) |
| Қай ортада тұрғанын анықтау | [`lib/runtime-env.ts`](../lib/runtime-env.ts) |
| Тақта | [`dashboard.json`](dashboard.json) |
| Дабыл ережелері | [`alerts.yaml`](alerts.yaml) |
| Кезекші агент | [`app/api/alerts/oncall/route.ts`](../app/api/alerts/oncall/route.ts) |

## Неге дәл осы өлшемдер

Жалпы HTTP көрсеткіштерін OpenTelemetry өзі жинайды. Мұндағылар —
осы жобада **нақты болған** ақауларды көрсететіндер:

- **`juzbook.reader.payload_bytes`** — оқу бетіне жіберілетін навигация
  жауабы бір рет 532 КБ-қа жеткен. Браузер соны талдауға мәжбүр болып,
  әлсіз ноутбуктерде бет баяу ашылатын.
- **`juzbook.catalog.query_ms`** — әкімші панелі каталогты 20 МБ күйінде
  сұрап, тақырыпты сақтаған сайын бір минутқа қатып қалатын.
- **`juzbook.search.empty`** — іздеу екі жүйенің қосындысы: кілт сөз
  (Postgres) және мағына (Turso). Біреуі құласа, екіншісі үнсіз жалғыз
  қалады — қате шықпайды, жай ғана нәтиже азаяды. Дәл сондықтан
  нәтижесіз сұранымдарды санаймыз.
- **`juzbook.gemini.key_rotated`** — кілт пулы таусылса, тест құрастыру
  мен флешкарта жасау тоқтайды.

## Орнату

### 1. Жинаушы

`OTEL_EXPORTER_OTLP_ENDPOINT` айнымалысын қойыңыз (Grafana Cloud, Honeycomb
немесе өзіңіздің коллектор). Ол **берілмесе, OTel мүлде қосылмайды** —
қолданба бұрынғыдай жұмыс істей береді. Бақылау жүйесінің құлауы
оқушыға әсер етпеуі керек.

Қызмет атауына орта қосылады (`juzbook-production`, `juzbook-development`),
сондықтан бір тақтада екі орта араласпайды.

### 2. Тақта

`dashboard.json` файлын Grafana-ға импорттаңыз. Үстіндегі «Орта» тізімінен
қай ортаны көретініңізді таңдайсыз.

### 3. Дабыл

`alerts.yaml` — Grafana Alerting пішімі. Шектер ойдан алынбаған, жоғарыда
айтылған нақты ақаулардан шыққан.

### 4. Кезекші агент

Үш айнымалы керек:

| Айнымалы | Не үшін |
|---|---|
| `ONCALL_WEBHOOK_SECRET` | Webhook-ты қорғайды. **Берілмесе маршрут жұмыс істемейді** |
| `ONCALL_GITHUB_TOKEN` | Issue ашу үшін (берілмесе, диагноз тек жауапта қайтады) |
| `ONCALL_GITHUB_REPO` | `owner/repo` түрінде |

Grafana дабылды жібергенде `x-juzbook-alert-secret` тақырыбын қосуы керек.

**Агенттің шекарасы әдейі тар.** Ол тек оқиды және issue жазады: код
өзгертпейді, деплой жасамайды, дерекқорға тимейді. Диагноз — болжам,
сондықтан issue соңында солай деп жазылады.

Алдымен `ONCALL_GITHUB_TOKEN`-сыз сынап көріңіз: сонда агент ештеңе
жазбайды, тек диагнозын қайтарады.

## Орталар

Орта **дерекқор бойынша** анықталады, қолданба қай жерде жүргені бойынша
емес — себебі қауіп дәл дерекқорда.

| Орта | Белгісі |
|---|---|
| Әзірлеу | `DATABASE_URL` жергілікті хостқа бағытталған |
| Алдын ала қарау | Қашықтағы база + `VERCEL_ENV=preview` |
| Өндіріс | Қалған жағдайдың бәрі |

Деректі өзгертетін скрипттер `assertWritable()` арқылы тексеріледі:
өндірістік базаға жазу үшін `JUZBOOK_ALLOW_PRODUCTION_WRITE=1` керек.

Бұл қорғаныс бос жерден қосылмады. Бір топтама түзету (қайталанған
бөлім атаулары, сурет туралаулары, тарау шекаралары) байқаусыз
**жергілікті** базада орындалып, өндіріске жетпей қалған — екеуінде де
дерек бірдей көрінгендіктен.
